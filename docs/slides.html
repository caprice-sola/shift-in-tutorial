Definition

What is an AI coding agent?

Not autocomplete. A loop that runs until a goal is met — or until something stops it.

Reasonplan the next step from the goal and what it knows
→
Actcall a tool: read, edit, run a command, open a PR
→
Observeread the result — output, diff, test failure
↻
  • It iterates faster than a human can supervise step by step.
  • Code, tests and decisions all happen inside one loop, not at separate points in time.
  • Everything we build today is a way to put quality into that loop.
Claude Code and Copilot agent mode both work this way. The tools differ; the loop is the same.
The thesis

Shift-left → Shift In

Shift-left

Move quality activities earlier in time.

The correct approach when humans write every line: find defects during design and component testing, not in production.

Direction: earlier in time.

Shift In

Move quality activities inside the agent's loop.

The agent generates, tests and gates its own work as it goes; the human's role moves from typist to verifier.

Direction: into the agent's loop.

If quality checks happen only before the loop (planning) or after it (CI, review), nothing checks the agent for most of the time it is working.
Theory

What "inside the loop" looks like

  • Hooks that run the test suite before the agent is allowed to finish a turn — feedback inside the loop, not after a push. (Ex 3)
  • Skills that encode a repeatable team technique, so the agent runs it consistently instead of improvising. (Ex 7)
  • Subagents that are responsible for one testing task, in a separate context. (Ex 5)
  • SLIs that define "good" and become pipeline gates. (Ex 1, Ex 4)
  • A human verification step — nothing is "done" until a person has reproduced and confirmed it. (all day)
Each exercise adds exactly one of these pieces. By Ex 7 they all run together on one real feature.
How we work

Mob programming, agent edition

Three people, one machine, and the agent does the typing. So the important role is the verifier, not the person at the keyboard.

Driverwrites the prompt
→
Agentacts
→
Mobreads the diff aloud
→
Navigatorchallenges one thing
→
Accept / rejectthen rotate
  • Rotate when a task ends, not on a timer — but a maximum of about 8 minutes per person.
  • Whoever rotates in reads the previous diff aloud and states intent before prompting.
  • The handover is the quality gate. The verification is the work itself, not extra administration.
This is how you stop team members becoming passive observers — a real risk when the agent writes code quickly.
Theory

Two anti-patterns to avoid all day

1 · High coverage, weak tests

Agents produce tests with high code coverage that check almost nothing.

What to do: use code coverage to find untested areas, not as a target. Check your test oracles by breaking the code on purpose. (Ex 3)

2 · Inverted test pyramid

Agents generate a slow end-to-end test for every change.

What to do: write each test at the lowest test level that gives confidence. The test strategy defines the target distribution. (Ex 1 → Ex 5)

Both problems increase as the agent produces tests faster and more cheaply.

Foundations

Definition

What is a prompt?

One instruction to the agent, for one turn: a goal plus constraints. It is not a magic phrase.

  • A good prompt states the outcome, the sources to use, and what "done" means.
  • A prompt is temporary: it applies to this turn only. Anything you would have to repeat in every session belongs in standing context instead.
  • Writing prompts is not the skill we teach today. Verifying the result is.

Weak

"Write a test strategy."

Stronger

"Using docs/slis.md and quality-characteristics.md, draft a test strategy with a target pyramid shape (weights per level) and a per-SLI test-level mapping."

Definition

Context — and the instructions file

The agent only knows what is in its context window: your prompt, files it read, tool output. It forgets everything between sessions.

  • Standing context is what gets loaded automatically, every session, for human and agent alike.
  • In Claude Code that file is CLAUDE.md at the repo root.
  • Write it once, carefully, and you do not have to explain the business context again in every session.
  • Keep it up to date: we update it as a deliberate step at the end of an exercise (version 2 in Ex 6).
Copilot equivalent: .github/copilot-instructions.md plus scoped *.instructions.md files for path-specific rules.
Definition

SLI, SLO — and why they drive testing

SLI — a measurable indicator of service behaviour.
"p95 server time to answer GET /{code}"

SLO — the target for that indicator.
"< 50 ms"

Quality characteristics — the prioritised quality attributes of this service (ISO/IEC 25010).

snip's SLIs

  • Redirect latency · p95 < 50 ms
  • Redirect availability · ≥ 99.9%
  • Resolve correctness · 100%
  • Create validation · 100%
  • Stats accuracy · 100%
SLIs have a job here: they decide what we test first (Ex 3, Ex 5) and what CI checks (Ex 4). If you cannot measure a quality attribute, you cannot use it as a gate.
Theory

A strategy written before any test exists

  • Written afterwards, a test strategy only describes what already happened.
  • Written first, it sets a target that later exercises can be measured against — so differences between plan and reality become visible instead of being ignored.
  • So it must be concrete and checkable: a table of test levels with a share of tests for each level, and one row per SLI naming the test level that will verify it.
  • "We will test the important things" is not a strategy. You cannot check whether you followed it, so it cannot guide any decision.
This helped in Ex 5 of the reference build: the strategy planned a second system test that turned out not to be justified, and the document made that difference visible.
Exercise 1 · Steps

Do this

  1. Read the three documents together — docs/business-context.md, quality-characteristics.md, slis.md. Do not skip this by asking the agent to summarise them. These documents are your test basis.
  2. Ask the agent to draft CLAUDE.md version 1: who the service serves, in priority order; the quality expectations; the SLI table; the working agreements; the technical conventions.
  3. Ask the agent to draft docs/test-strategy.md version 1: the target share of tests per test level, a table mapping each SLI to a test level, and a plan for checking the test oracles.
  4. Read both documents aloud together. Ask: could this text belong to any application? If yes, it is generic — reject it and ask the agent again.
  5. Commit. No application code changes in this exercise.
Watch for: approving a generic CLAUDE.md without reading it. Ask the agent: "does this describe our business context?"
Facilitator: step 1 is the one mobs skip. Hold them to actually reading the three docs — everything downstream is derived from them. ~8 min read, ~15 min drafting, ~5 min read-back.

Exercise 1 · Learning points

What just happened

  • The context file is a work product you own. It is version-controlled, reviewed and updated — treat it like source code, not like a configuration file nobody reads.
  • Specific is better than generic. An instructions file that could belong to any repository uses context space and adds no value.
  • The strategy comes first so later exercises can be measured against it — including when reality disagrees with it.
  • SLIs show where to put test effort first. We use them for exactly that, all day.

The agent as collaborator

Run an AI code review, check the diff together, and let the agent perform a real action outside the repository: open a pull request.

10:00–10:45 · 45 min Deliverable: minimal CI workflow + first reviewed PR Fallback branch: solution/m2-review
Here the verification steps become a habit. Every later exercise depends on them.
Definition

Tools — how an agent acts outside the chat

A tool is an action the agent can perform: read a file, edit a file, run a shell command, call an API.

  • Local tools — reading and writing files, and bash, which gives the widest access of all.
  • External actions — today via the gh CLI: issues, PRs, CI status, all from the terminal.
  • MCP (Model Context Protocol) — an open protocol for connecting external systems as tools (GitHub, Jira, a database), each with its own authentication and permissions.
  • The more an agent can reach, the more damage one mistake can cause. Limit the tools deliberately — we do exactly that in Ex 5.
Copilot equivalent: GitHub and Playwright MCP servers are enabled by default in agent mode. Today we use gh — less setup, and it is already authenticated.
Definition

AI code review

Asking the agent to read code and report defects in it. No code is executed, so this is a form of static testing.

Good at

Wide coverage: unhandled paths, missing validation, weak error handling, differences between files. It is fast, and it does not defend its own code.

Bad at

Prioritisation: it reports a serious security defect and a small formatting comment in one flat list, with the same confidence.

  • So your job is to evaluate the findings: which are real defects, which are false positives, and which ones affect our SLIs?
A finding is a claim, not a fact. Reproduce it before you fix it.
Theory · the verification steps

The verification ritual

Four steps, for every change you accept. These steps are the quality gate.

  1. Read the diff — out loud, together. Not the agent's summary of the diff. The diff.
  2. Run it — the application, the endpoint, the command. Check the behaviour, not the description of it.
  3. Question one statement — take one sentence the agent wrote and check whether it is true.
  4. Accept or reject — then rotate. The person rotating in re-reads the diff.
Opening a pull request is an action outside the repository. Do these four steps before it, not after: once it is pushed, other people can see it.
Exercise 2 · Steps

Do this

  1. Ask the agent to review the starter application for real defects. Let it read the code itself.
  2. Evaluate the findings together. Which are real defects? Which are false positives? Which ones break a published SLI?
  3. Rotate on one fix: driver prompts → agent acts → mob reads the diff aloud → navigator challenges one specific thing → accept or reject → rotate. Repeat for a second finding.
  4. Add a minimal CI workflow — install the package and check that it imports. No tests yet; that is Ex 3.
  5. Once the mob has actually accepted the changes, ask the agent to open a PR via gh.
  6. Read the PR as it appears on GitHub before moving on.
Two findings, not five. This exercise is about the verification steps, not about finding everything. Leaving known defects open is the correct result.
Facilitator: watch for a mob accepting the first fix without reading the diff — stop them if it happens; that is the exact anti-pattern this exercise exists to interrupt. Keep the collision-related finding OPEN — Ex 3 needs it. Confirm gh auth status before step 5 if this is the day's first GitHub action.

Exercise 2 · Learning points

What just happened

  • A fix that looks correct can change behaviour silently. In the reference build, a URL-validation fix looked correct at first reading — but it changed the input (added a trailing slash, lowercased the host), which broke the rule "a link resolves to the exact URL it was created for."
  • Reading the diff is the work. The summary above the diff is only the agent's own description of what it did.
  • Evaluate findings; do not fix everything the agent reports. Rank them by their effect on the SLIs.
  • Check actions that leave the repository, before they happen. The agent can open pull requests, write comments and close issues.

Unit tests + the loop hook

Generate unit tests, find weak test oracles by breaking the code by hand, then run the test suite inside the agent's loop.

11:15–12:00 · 45 min Deliverable: tests/unit/, tests/api/, an oracle check, a Stop hook Fallback branch: solution/m3a-unit-hook
This is the turning point of the day — the moment where shift-left becomes Shift In.
Definition

Code coverage shows gaps, not quality

Statement coverage answers "was this line executed?" — not "would a test detect a defect in it?"

  • Use it to find untested areas: which SLI-related and business-critical paths were never executed by a test?
  • Test those first. Do not use a coverage percentage as a target — an agent can easily produce tests that raise the number without testing anything.
  • A file with 100% statement coverage can still have no test that would detect a defect in it.
In the reference build, the collision test covered the retry line completely — and still passed when the retried code was replaced with None.
Definition

The oracle problem

Test oracle: the source that tells the test what the correct result is. In a unit test, that is the assertion.

The problem: a test can execute the code and still check nothing meaningful. It passes whether the code is correct or not.

The check: break it on purpose

Change one line to something wrong (flip a comparison, return None) and re-run the tests.

A test fails → the test oracle works. Good.

All tests still pass → no test checks that behaviour. That is a missing assertion.

Three minutes, by hand, no extra tool. This is mutation testing done manually. The tool mutmut does it automatically for a whole module — something to try later, not today.
Definition

What is a hook?

A command that the agent tool runs automatically at a defined point in the agent's work. The tool always runs it; the agent cannot decide to skip it.

  • Example points: before a tool runs (PreToolUse), after a tool runs (PostToolUse), and when the agent tries to end its turn (Stop).
  • A Stop hook can block: return {"decision":"block","reason":"…"} and the agent must keep working — with your reason as its next instruction.
  • An instruction is a request that the agent can ignore. A hook is a rule that the tool enforces. That difference is the point.
  • It must stay fast — it runs on every turn.
Copilot equivalent: hooks exist (e.g. preToolUse), configured differently — same idea, different file.
Facilitator: the reference build's first hook nested decision/reason under hookSpecificOutput — no error, just a silent no-op. Verify the JSON shape against current docs, and test the hook by piping fake JSON at it before trusting it live.
The turning point

Where shift-left becomes Shift In

BeforeTests run when a person remembers to run them, or in CI after a push. Between those points, nothing checks the agent.
→
AfterThe agent cannot end its turn while a test is failing. Test feedback arrives inside the loop.
  • Feedback time drops from "minutes, after a push" to the same agent turn.
  • The agent now fixes the defects it introduced before you see them, using the test output it just received.
  • Everything else today repeats this idea: put the test activity where the agent is already working.
When the hook blocks the agent for the first time, say so out loud. This is the central moment of the day.
Exercise 3 · Steps

Do this

  1. Add pytest and pytest-cov as a test extra.
  2. Write a unit test for the defect still open from Ex 2 and run it to confirm that it fails.
  3. Fix the defect, then run the test again to confirm that it now passes (confirmation testing).
  4. Add a few API-level tests — only that each route returns the correct status code and response structure, not every input variation.
  5. Break the code on purpose: change the collision-retry line to code = None and re-run the suite. Does it go red — or stay green on broken code?
  6. If all tests still pass, an assertion is missing. Make the assertion stronger, run the tests again to confirm they now detect the broken line, then undo the change to the code.
  7. Write the Stop hook and its settings. Test the hook itself by sending it a test JSON input — once with passing tests, once with a failing test — before you rely on it.
  8. Show it working: break one test on purpose, ask the agent to make any change, and confirm that the hook does not let the agent finish.
Facilitator: this is the tightest block of the morning. Steps 5–6 are deliberately cheap — about three minutes by hand — so nobody should skip them; if time is short, cut depth in step 4 instead. The mob must do the breaking itself: watching a green suite survive obviously-broken code is the point, and it doesn't land secondhand.

If you're behind, start here

Prompt 1 · write a failing test first
Add pytest and pytest-cov as a [test] extra. Then write ONE unit test that proves the short-code collision bug: an existing code must never be silently overwritten. Run it and show me it failing — do not fix the bug yet.
Prompt 2 · check the test oracle
In src/snip/shortener.py, change the collision-retry line to code = None and run the suite. If it still passes, tell me exactly which assertion should have caught it and why it didn't. Don't fix anything yet, and leave the broken line in place so we can see it fail once the assertion is stronger.

Exercise 3 · Learning points

What just happened

  • A passing test does not mean the behaviour is checked. Breaking the code on purpose shows you the difference — three minutes, no extra tool.
  • Weak assertions to watch for: checking that something happened without checking what happened. pytest.raises(SomeError) checks the exception type, not its content.
  • An enforced rule is better than a written intention. "Always run the tests" in an instructions file is a request the agent can ignore. A Stop hook cannot be ignored.
  • Testing now happens inside the loop. The test fails, the agent sees the failure and fixes it, before a person is involved.
  • Check the hook's expected output format in the current documentation. A hook with the wrong format does not report an error — it simply does nothing.

4

The CI pipeline

Check every commit in CI — and turn one published SLI into a real pipeline gate.

12:00–12:30 · 30 min Deliverable: .github/workflows/ci.yml with an SLI gate Fallback branch: solution/m3b-ci
This is more than "run the tests in CI". The exercise is to make CI enforce a service target that is written down (the SLO in docs/slis.md).
Definition

CI, and what a gate is

  • CI (continuous integration) — on every push, a clean machine checks out the code, installs it and runs the checks. So "it works on my computer" cannot happen.
  • A gate — a check that stops the change when it fails. If a failing check does not stop anything, it is only a report.
  • An SLI-based gate — it checks the documented SLO, not a convenient number: 95th percentile redirect time under 50 ms, measured against a real running server.
  • This makes the target in docs/slis.md executable. The document now has an effect.
Do not relax the threshold because you expect flaky tests. Measure the real margin first: the reference build measured about 0.6 ms against the 50 ms target — about 80 times margin.
Theory

Two loops, two jobs

Inside the loop (the Stop hook)

Runs on every agent turn. Must stay fast — a few seconds.

Scope: unit and API tests. Detects defects the agent introduced, immediately.

After the push (CI)

Runs on every push. It is allowed to be slow.

Scope: clean install, the full test suite and the SLI gate — a real server and real requests.

  • Keep this separation explicit: if the slow gate is added to the hook, the hook becomes slow and people will switch it off.
Shift In does not replace CI. It means CI is no longer the first place where quality is checked.
Exercise 4 · Steps

Do this

  1. Choose one SLI to check in the pipeline. Redirect response time is the simplest first choice.
  2. Write a separate test that starts a real server, sends real requests and compares the result with the documented SLO — do not relax the threshold.
  3. Confirm that the Stop hook does not run this slow test. Check it; do not assume it.
  4. Update the workflow: keep the install check, add the unit and API tests, then add the SLI gate as a separate, named step, so that a failure shows which test level failed.
  5. Push and confirm CI is green on GitHub — not just locally.
Step 5 fits well before lunch: push first, then read the CI result.

Prompt 2 · keep the hook fast

Exercise 4 · Learning points

What just happened

  • An SLI with no pipeline check is only a document. One executable check makes the whole document binding for the team.
  • Measure before you relax a threshold. Relaxing it because of failures you have never observed silently lowers the service target.
  • Fast and slow feedback have different purposes. Protect the fast one: if the check inside the loop becomes slow, people will switch it off.
  • Name your pipeline steps clearly. When CI fails, the step name should already tell you which test level failed.

5

System tests as a subagent

Delegate Robot Framework test suites to a subagent with a limited scope — and keep the test pyramid in the right shape while doing it.

13:30–14:15 · ~45 min Deliverable: system-test subagent + tests/system/ Fallback branch: solution/m4-system (after Ex 6)
This is where teams add too many system tests. Watch for it.
Definition

What is a subagent?

A second agent, started by the first one, with its own separate context, its own instructions and a limited set of tools.

  • Separate context — it does not receive the main conversation, and its output does not fill your conversation. It returns a summary.
  • Limited responsibility — one task, explicit rules, including what it must not do.
  • Limited tools — give it only what the task needs, and write the allowed directories into its instructions as well.
  • Best for one task, delegated once. Not suitable for a task that needs discussion — it cannot see your conversation.
Copilot equivalent: a custom agent profile with its own instructions and MCP scoping. Robot Framework itself is tool-agnostic.
Definition

The pyramid — and why it inverts

Unit tests (ISTQB: component testing) — fast, exact, many. They show which line is wrong.

API tests (component integration testing) — an in-process client through routing, validation and handlers.

System tests (system testing) — a real server process, real network connections, real HTTP. Slow and few, but the only way to test the deployed behaviour.

Inverted test pyramid

The anti-pattern: many slow end-to-end tests and few fast ones. The suite is slow, the tests fail intermittently, and a failure does not show which component is wrong.

An agent makes this more likely — writing 20 end-to-end tests now costs almost nothing, so only your rules limit it.

Working agreement: write each test at the lowest test level that gives enough confidence.
Theory

When is a system test justified?

Only when the behaviour cannot be tested at a lower test level.

Justified

A real server process, real network connections, real deployment configuration. The most-used path, end to end: create a link → follow it → check the statistics.

Not justified

"It goes through routing, validation and error handling." The API-level test client already does exactly that: same input, same assertion, only slower.

In the reference build, the first suite added two test cases for exactly that reason. Both were exact copies of existing API tests. They were found in review and deleted, and the test strategy document was corrected.
Exercise 5 · Steps

Do this

  1. Check how subagent files are defined in the current documentation before you create one: file location, required fields, tool restrictions.
  2. Write the subagent's rules with a strict limit: a system test is justified only when the behaviour cannot be tested at the API level. State this explicitly in its instructions.
  3. Let it produce one test suite: the most-used path, end to end — create a link → follow it → check the statistics.
  4. Run the suite against a real server and confirm that it passes. A test suite you have not executed is only a claim.
  5. Review the result together: does every test case meet the rule? Delete the ones that do not.
Adding no extra test case can be the correct answer. Do not add test cases only because a document mentioned "one or two more".
Facilitator: if a mob's subagent produces duplicates of the API tests, that is the best possible outcome — make them find it, then delete them and correct the strategy doc. That story is worth more than a clean first run.
Exercise 5 · Example prompts

If you're behind, start here

Prompt 1 · create the subagent
Check the current documentation for how subagents are defined — file location, frontmatter fields, tool scoping — then create a system-test-writer subagent. Its job: Robot Framework suites in tests/system/ only. Ground rule to state explicitly: a system test is justified ONLY if it proves something tests/api/ cannot — real process, real sockets. Not "it exercises routing and validation." It must read docs/test-strategy.md and the existing tests before writing anything, and it must run what it writes.
Prompt 2 · delegate the test suite
Use the system-test-writer subagent to add one test suite covering the most-used path: create a link, follow it, check the statistics — against a real running server. Report back what it added and what it deliberately chose not to add.
Prompt 3 · check every test case
For each case in tests/system/, show me the tests/api/ test that already covers the same behaviour, or state clearly what only a real server can prove here. Delete any case that fails that test.
Exercise 5 · Learning points

What just happened

  • Delegation needs a narrow, written scope. A subagent with one task and explicit "do not do this" rules is far more reliable than an open request to "write some system tests".
  • Cheap test generation makes discipline harder. Writing tests used to be slow, and that effort protected the pyramid. Now only your rules protect it.
  • "It goes through the whole system" is not a justification. Ask what only this test level can verify.
  • A test that was never executed is only a claim. Make execution part of the subagent's Definition of Done.
6

System regression in the pipeline

Add the slow test suite as a separate CI job — and update the agent's standing context to match the completed test pyramid.

14:15–14:45 · ~30 min Deliverable: second CI job + CLAUDE.md v2 Fallback branch: solution/m4-system
Theory

A separate job, not a slower step

  • CI jobs run in parallel by default, so moving the slow suite into its own job does not slow down the fast job.
  • A reviewer sees immediately which test level failed: the fast checks, or the system tests?
  • Separate the dependencies as well: a [system] group separate from [test], so the fast job never installs libraries it does not use.
  • Upload the system-test report as a CI artifact — you cannot analyse a failed system test without its log.
You now have three levels of feedback speed: the hook (seconds, every turn) → the fast CI job (about a minute, every push) → the system-test job (slower, running in parallel).
Theory

Keep the instructions file up to date

The test pyramid is now complete. If CLAUDE.md still describes this morning's state, the agent is working from an out-of-date description.

  • Update it at the end of an exercise, as a deliberate step — not "some time later, when we remember".
  • Version 2 should describe all three test levels in one place: what belongs at each level, and what does not.
  • Add the working agreement for delegation: when to give system-test work to the subagent, and the rule it must apply.
  • Out-of-date standing context is worse than none: it is wrong, and the agent follows it in every session.
This is a repeating step, not a one-time task for Ex 6. Ex 7 uses whatever you write here.

Definition

What is a skill?

A reusable procedure in a folder that the agent loads when it is relevant: your team's method, written down once and then applied the same way every time.

  • It contains instructions, and optionally scripts or reference files, which the agent loads when needed.
  • It runs in the current conversation, so it can have a real dialogue with the team.
  • Use it so that the agent does not invent a different method each time you ask.

Definition

Example Mapping

A structured Three Amigos conversation (method by Matt Wynne) using four colours of card.

Yellow · Storyone sentence: actor, action, outcome
Blue · Rulesthe acceptance criteria, short and testable
Green · Examplesconcrete inputs and expected outcomes per rule
Red · Questionswhat nobody present can answer yet
  • Rules are proposed one at a time and confirmed — not delivered as a finished list.
  • Examples make hidden disagreement visible. Two people can agree on the wording of a rule and still expect different numbers.
  • Many red cards is a valid result: the story is not ready yet. That is a finding, not a failure.
Definition

Untrusted input and prompt injection

Text that the agent reads can contain instructions written for the agent, not for you.

  • The dangerous combination is all three together: the agent can read external content, it has write access to your repository, and it can perform actions outside the repository.
  • Issues, pull request comments, web pages, documents, README files of dependencies — all of this is external content that your team did not write.
  • The displayed page is not the raw text. A GitHub page does not show HTML comments. The raw text that an API or CLI returns does show them.
  • Read the raw text first, completely, before summarising it or acting on any part of it. Every time, not only when something looks suspicious.
This is not a theoretical example. In the next ten minutes you will give an issue written by someone else to an agent that can write to your repository.
Exercise 7 · Part 1 · Steps

Refine the story

  1. Use the prepared issue: link expiry. Do not read the GitHub page first.
  2. Ask the agent to fetch the issue's raw content and inspect it in full before summarising or acting on any of it.
  3. Discuss what it found together before you continue.
  4. Run the Example Mapping skill on the content you have now checked.
  5. Do the interview as a team: confirm the story, then the rules one at a time, then examples for each rule, written as Gherkin scenarios.
  6. Write down every open question. Do not let the agent decide one silently.
  7. Produce the acceptance criteria document.
Facilitator: set up the injection beat deliberately — do not let the mob glance at the rendered issue first. The raw body carries an HTML comment, invisible on GitHub, asking whoever implements the feature to quietly undo the day's validation and hook work. Ask: what would have happened if nobody looked at the raw text? Budget 5 minutes for this beat, no more.

Exercise 7 · Part 2 · Steps

Build the feature

  1. Read the acceptance criteria document together before writing code. Does the team agree with what is about to be built?
  2. Write the tests first, from the scenarios in that document. Run them and confirm that they fail before you implement anything.
  3. Implement the rules. Let the Stop hook run — do not switch it off to be faster.
  4. Break one line of the new code on purpose, run the tests again, and confirm that a test fails. If all tests still pass, an assertion is missing.
  5. Run a smoke test against the running application by hand, with real requests — not only the automated tests.
  6. Open a pull request and read what CI reports. Do not merge it into the fallback branch.
Passing tests are necessary, but not sufficient. The reference build contained a crash while all tests passed. It was found only by reproducing it against the running application.

The message

Shift In, in one slide

Shift-left means testing earlier in time. Shift In means putting quality engineering inside the agent's loop, so the agent writes code, runs tests and checks its own work as it goes.

  • The hook that runs the tests before the agent stops.
  • The skill that contains a repeatable team method.
  • The subagent that is responsible for one testing task.
  • The SLI that became a pipeline gate.
  • The person who reproduces and confirms every accepted change.
These are not extras added to AI coding. They are how quality is kept when the agent works on its own.

Take away

What to do when you are back at work

  • Write the instructions file first. One hour, based on your real project documents, is worth more than a week of learning prompt techniques.
  • Add one hook. Tests, a linter or a type check before the agent may stop. This gives the biggest effect for one hour of work.
  • Choose one SLI and check it in the pipeline. Make one documented target executable.
  • Break one line on purpose in your most critical module and run your tests. Expect a surprise. (mutmut does this automatically when you want it for a whole module.)
  • Make "read the diff" a team rule, agreed out loud, and record who approved each change.
